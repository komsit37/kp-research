For platform and data engineers

Thai stock data platform

A simple design for downloading data, keeping the original files, cleaning them into stable tables, running jobs on time, and later connecting a broker safely.

01 / Main choices

Start small; keep the boundaries clear

StoragePostgreSQL + Parquet

Enough for the first platform. Add more systems only after a measured need.

CollectionOfficial API first

File download second, public-page crawler third, browser automation last.

JobsOne scheduler owns runs

Every job has a time, checkpoint, retry policy, owner and freshness target.

TradingSeparate service

Research code never sends an order directly to the broker.

03 / Connector ladder

Use the least fragile access method

LevelMethodUse it forRules
A · PreferredOfficial API or bulk filePrices, reference data, company reports.Follow pagination; save the full reply; record source version and terms.
B · AcceptablePublic HTML crawlerPublic pages when no API exists.Use normal HTTP first; rate-limit; cache; detect page-layout changes.
C · Last resortBrowser automationPages that require JavaScript to show public data.Slow and fragile. Never use it to bypass login, access rules or licensing.
D · RealtimeWebSocket / MQTT streamLive price, minute bars and buy/sell offers.Heartbeat, reconnect, sequence tracking, local recording and gap alerts are required.
E · TradingBroker API adapterOrders, fills, cash and holdings.Separate credentials and process; strict limits; every action stored before sending.
Do not automate TISCO Streaming. TISCO is not currently listed for the retail Settrade Open API. Keep it manual or use a separate supported broker adapter.
04 / Database design

Two stores are enough for the first version

PostgreSQL handles clean records and state. Object storage + Parquet handles original files and large history.

Store / tableWhat goes thereKey design point
Raw object storeOriginal API reply, downloaded file, HTML, PDF and stream batches.Path by source/date; checksum; retrieval time; never overwrite.
instrumentsOne internal ID for each stock, fund or other product.Source symbols are aliases; symbol changes do not create a new company by accident.
trading_calendarOpen days and market sessions.Jobs use the calendar, not hard-coded weekdays or hours.
daily_bars / minute_barsOpen, high, low, close, amount traded and value.Keep raw and adjusted prices; partition large tables by date.
trades / book_updatesIndividual trades and changing buy/sell offers.Recent data may live in Postgres; move long history to Parquet.
documents / factsCompany reports plus numbers parsed from them.Store when the public could first see the report, not only its reporting period.
actionsDividends, share splits, rights issues, symbol changes and delistings.Needed to calculate correct historical returns.
orders / order_events / fillsRequested orders and every later broker update.Append events; never hide history by replacing the last status.
ingestion_runs / watermarksJob result and the last complete source position.Makes retry and backfill safe and repeatable.

Common fields on collected records: source, instrument_id, event_time, received_at, available_at, raw_object_id, ingestion_run_id and parser_version.

05 / Scheduler

Jobs run from the market calendar

Dagu, Airflow, Dagster or Prefect can all work. Pick one already operated by the team; do not mix several schedulers at the start.

Job familyWhenCheckpointFail if
Reference dataBefore each open dayBusiness date + source versionMissing active symbols or unexpected large change.
Company report pollerEvery few minutes during release hoursLast source ID/timePoll is stale, IDs go backward or parser fails.
Live market recorderStart before session; stop after closeLast message sequence/timeHeartbeat lost, clock drifts or a gap cannot be filled.
Daily price loadAfter official daily file is readyBusiness dateCoverage/count differs from source or duplicate rows appear.
Company action loadNightly and on-demand backfillLast changed recordPast adjusted prices change without a new action or correction.
Broker checkBefore session, during trading, after closeBroker event/order IDCash, holdings, open orders or fills disagree with our records.

06 / Reliability rules

Design every job to run twice safely

Keep the originalA parser bug can be fixed by replaying raw data. Without raw data, the history is lost.
Use stable keysThe same source record loaded twice must update or do nothing—not create a duplicate.
Track two timesStore when the source says an event happened and when our system received it.
Use watermarksEach connector records the last complete page, ID, timestamp or stream sequence.
Check freshnessA successful job with old data is still a failure. Alert on age and expected coverage.
Version parsersWhen a page or API changes, we can identify which rows used each parser version.
Quarantine bad rowsKeep malformed records for review; do not silently drop or guess values.
Reconcile sourcesCompare daily totals, active symbols and broker positions against an independent source.
07 / Trading boundary

Put one guarded service in front of the broker

Order flow
StrategyCreates an order intent; cannot call broker
Risk gateChecks size, price, cash, duplicate and kill switch
Order serviceStores intent, assigns one ID, then sends
Broker adapterSettrade API in sandbox, paper or live mode
Return flow
Broker updatesAccepted, rejected, partly filled, filled, cancelled
Event logAppend every update; preserve broker IDs
ReconcilerCompare orders, cash and holdings regularly
AlertsStop trading on unresolved mismatch or stale feed

Use separate credentials, processes and permissions for research, paper and live. A strategy promotion changes configuration—not the order path.

08 / One simple example

AOT data through one market day

Before open
Scheduler loads the official calendar and active-symbol list. AOT maps to one internal instrument ID.
During session
Settrade stream reader stores price and buy/sell-offer updates. Heartbeat and message-time checks watch for gaps.
Report arrives
SEC/SET connector saves the original file, its public time and checksum; a parser writes clean facts linked to that file.
After close
Official daily price replaces any temporary live-derived close. Quality job compares volume, value and symbol coverage.
Research
A query can now ask: “How did AOT move after the report?” using only data that was public at each time.
09 / Build order

Deliver useful pieces in four steps

StepBuildExit test
1 · Daily researchRaw store, PostgreSQL, security master, daily prices, actions and company reports.Re-run any date with no duplicate; reproduce one known company event.
2 · Reliable crawlingScheduler, watermarks, retries, parser versions, freshness dashboard and alerts.Recover from API/page failure without manual database edits.
3 · Live recordingSettrade stream reader, minute bars/book storage, heartbeat, reconnect and gap checks.Record a full week with measured completeness and known gaps.
4 · Paper tradingRisk gate, order service, supported broker sandbox, event log and reconciliation.Pass place/change/cancel/partial-fill/reconnect tests before any live key is enabled.

Expected outside-team output: architecture diagram, source-access proof, schemas, job list, one batch connector, one live connector, sandbox order demo, failure-test results, operating cost and license notes.
